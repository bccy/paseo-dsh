dsh-paseo adds a native provider to Paseo for DeepSeek Harness (`dsh`), so a Paseo agent runs as a DSH session instead of an ACP client. The conversation stays in Paseo's normal agent view, and the plugin adds no screens of its own. It is a community plugin, not an official DeepSeek or Paseo product.

One provider connection owns one `dsh --profile paseo` child process on the daemon machine and talks to it over a local stdio bridge; every Paseo agent session on that connection shares it. The working directory, the model route and the MCP servers are handed to that process **per session** (DSH keeps them per session id and never calls `chdir`), so sessions in different workspaces run side by side and a new agent skips the CLI cold start. The exception is the environment: it is process-wide, so the values the first session opened with stay in effect, and a later session asking for something different gets a warning on its timeline naming the keys that did not apply. The process runs as your operating system user with the daemon's environment, so the credentials and permission policy are the ones DSH already uses; the plugin adds no sandbox of its own. Model and reasoning-effort choices come from the catalog DSH reports for the profile, so they follow your DSH configuration.

DeepSeek Harness must be installed and logged in on the daemon machine, with `dsh` on the daemon's `PATH` or set through the provider command override. The plugin needs Paseo 0.9.2 or newer and Node.js 20.4 or newer on the daemon (the bridge uses `AbortSignal.any`, added in Node 20.3, and `Symbol.dispose`, added in Node 20.4; only Node 22.23.1 has actually been tested and the package declares no `engines`), and DSH 0.2.1-rc.2 is the tested line. On first use it provisions `~/.dsh/profiles/paseo`, and it never overwrites an existing profile file, so local edits to `cordis.patch.yml` survive reloads.

Composer features are passed to DSH rather than emulated. Attached images are admitted into DSH's attachment store, `/` commands and user-invocable skills come from DSH's registry, and steering, plan mode, question cards, tool approval cards and permission prompts render as normal Paseo items. The session menu can switch the agent preset and permission mode when the profile declares them, the composer shows the context window and current occupancy that DSH reports, and each answer carries a small line with its first-token latency and output speed. A background-jobs pill reports DSH jobs (live count while running, total when idle), and goal/workflow events render as timeline rows, including workflows that keep running across turns. Sessions persist by DSH session id, so a reopened agent resumes its context, and Paseo can list and import existing DSH sessions; an imported session replays its messages into the timeline. A session may also carry its own system prompt when the profile mounts the `systemPrompt` service.

Images work both ways. The model receives attached images, and when a tool produces an image DSH's attachment service gives the bridge a host path; the bridge stamps `hostPath` on the image block and the plugin emits a `file://` Markdown row that Paseo loads through its file RPC. Attached images are still delivered per the route's declared modality: a route that declares text only turns them into placeholder text.

Known limits: one `dsh` process serves every session on a connection, so a crash or a stalled frame in that process affects all of them at once (the plugin reports the failure per session rather than hiding it). The environment is process-wide too, so `PASEO_AGENT_ID` / `PASEO_AGENT_CWD` stay those of the first session; Paseo CLI calls made through bash tools from a later session (heartbeat, schedule, agent send) therefore target the first agent — DSH has no per-session shell-env extension point today, so this is documented rather than silently worked around. Reloading the plugin or restarting the daemon ends a running turn, and the session has to be resumed. The provider id is `deepseek-harness-native`, which keeps it separate from an ACP `deepseek-harness` provider when both are installed. Windows and native iOS and Android clients are untested.
