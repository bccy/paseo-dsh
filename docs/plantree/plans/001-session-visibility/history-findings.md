# 历史翻页定位

阶段：已按用户的对照判据收尾；[实测证据](history-evidence.md)。本轮不做历史性能代码改动。

## 用户确认
- 等待仅发生在 DSH 会话，其他 Provider 正常。
- 主要使用 iOS App。

## 已核实链路
- 客户端在本地历史窗口耗尽后发起 `direction: before` 请求，页大小为 40。
- 请求经过 `fetch_agent_timeline_request` → `ensureAgentLoaded` → `fetchTimeline` → 返回分页响应。
- 常驻 agent 从内存投影取页；此路径没有 DSH 专属分支。
- 冷恢复可能等待 provider 历史恢复。当前 DSH 插件的 `paseo/history` 读取完整原始历史，再映射时间线。
- 部分工具详情包含完整内容，可能放大单页载荷和前端渲染成本，需要测量。

## 证据限制
- 第一轮日志只找到一条约 3.58 秒的 OpenCode 冷恢复样本，不能用作 DSH 根因证据。
- 现有 DSH 会话历史数据大小只提示风险，不能证明向上翻页时每次都重读完整历史。
- 通用客户端的 40 条分页与无预取只是已知行为，不能解释“仅 DSH 慢”。

## 下一步
- 如果后续 iOS 真机或 relay 路径出现可复现慢样本，再按同条件、同规模页记录 RPC 与渲染分解。
- 不对用户原始数据做截断，也不把短会话的 after 请求等同于长会话 before 多页对照。
